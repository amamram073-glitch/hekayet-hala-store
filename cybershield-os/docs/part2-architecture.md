# CyberShield OS — تصميم توسعة Part 2

## المبدأ

توسعة تدريجية للبنية الحالية فقط؛ لا حذف لوحدات الأصول والفحوص والنتائج والمخاطر والحوادث والتقارير والفريق والمحلل الحالي. تبقى واجهات `/api` الحالية والتوافق الخلفي، وتضاف الجداول والترحيلات والمسارات الجديدة في حزم مستقلة. تبقى المؤسسة المحددة في السياق الموثق هي مصدر `organization_id`؛ لا يؤخذ مطلقاً من حمولة المستخدم.

## خط معالجة الأحداث

`POST /api/events/ingest` يستخدم مفتاح مؤسسة API بامتياز `EVENT_INGEST`، مخزن بصمةً فقط وقابل للإبطال/التدوير. بعد التحقق من حد الحجم والحقول والنطاق والحد المعدلي، تطبع الخدمة المصدر والوقت والشدة ومضيف/عنوان IP/اسم المستخدم/الأصل/البيانات الوصفية، وتعيّن المؤسسة من مفتاح API فقط، وتحفظ الحدث، ثم تضع معرّفه في Celery/Redis. يعالج عامل الخلفية قواعد كشف ثابتة ومنظمة (لا شيفرة قابلة للتنفيذ في شروط القواعد)، ويكتب تنبيهات وأسبابها وروابط الأحداث. قواعد الارتباط تستخدم نافذة زمنية وحدوداً معلنة؛ المطابقة تنشئ تنبيهاً بلغة احتمالية لا حكماً آلياً بأن الفعل خبيث.

يستعمل `SecurityEvent` الحالي كجدول الأحداث القانوني ويضاف إليه ما يلزم من حقول مطبّعة وفهارس مع migration إضافية؛ لا تنشأ نسخة موازية تشتت بيانات `/api/events` الحالية. المسارات القديمة تظل مدعومة.

## البيانات ومسارات API الجديدة

- `ApiKey`: المؤسسة، الاسم، بادئة العرض، البصمة، الامتيازات، وقت آخر استخدام، الإبطال، المنشئ. يعرض المفتاح الكامل مرة واحدة عند الإنشاء فقط.
- `DetectionRule` و`Alert` و`AlertEventLink`: شروط محدودة بقائمة حقول/عمليات مسموحة، حالة alert المنصوص عليها، الدليل والأحداث المرتبطة، والأصل والمستخدم والقاعدة والدرجة الزمنية.
- `ThreatIndicator`: نوع/قيمة مطبّعة/الثقة/المصدر/الوسوم/الظهور الأول والأخير؛ مزودات TI واجهات مجردة، بلا مزود خارجي مفروض.
- `Investigation` و`Case` و`AnalystTask` و`Case/Investigation links` و`EvidenceMetadata` و`ApprovalRequest`: عزل مؤسسة، تسلسل تاريخي، صلاحيات محلل/مدير، تغييرات حالة مدققة؛ لا تنفيذ تلقائي حساس بلا موافقة مسجلة.
- `WebhookEndpoint` و`WebhookDelivery`: وجهات مُدارة، توقيع HMAC، قائمة أحداث مسموحة ومحاولات إعادة محدودة. يتحقق التطبيق من عناوين الوجهات لمنع SSRF، ويتجنب الأسرار في السجلات.

مسارات REST المتوافقة مع الحالية تشمل إدارة مفاتيح API، الإدخال، `/alerts`، `/investigations`، `/cases`، `/tasks`، `/indicators`، قواعد الكشف، لوحات SOC، الصحة والاستعداد. كل قارئ يقيّد SQL بمؤسسة المستخدم، وكل معرف مورد خارجي غير موجود/خارج المؤسسة يعطي 404.

## الزمن الحقيقي وواجهات المستخدم

يربط `/api/ws` مستخدماً مصادقاً مع التحقق من الأصل والجلسة، ويستخدم Pub/Sub المؤسسة كي تصل إشعارات العامل إلى الاتصال الحي؛ لا تحتوي الرسائل على أحداث مؤسسة أخرى. صفحة SOC تعرض قيماً مشتقة من قاعدة البيانات/نافذة الأحداث لا بيانات تجريبية. تضاف صفحات تنبيهات وتحقيقات وذكاء التهديدات ومهام/حالات ومركز SOC عبر مكونات مستقلة وتحميل كسول. تبقى اللغة العربية وRTL والإنجليزية وLTR والنمط الداكن والتجاوب.

## AI والتحليلات

يعاد استخدام المحلل الحالي، مع اختيار سجلات المؤسسة المحددة فقط، وتضمين مراجع أدلة موجودة فعلياً (معرفات الحدث/التنبيه/الأصل)، ثم التحقق من أن كل مرجع معاد يعود لسجلات السياق قبل عرضه. المساعد تحليلي فقط، لا ينفذ أوامر أو تغييرات؛ الإجراء الحساس يمر عبر مسار موافقة وصلاحية وتدقيق منفصل. لا يُقدّم اعتقاد غير مدعوم أو يختلق دليلاً.

## الأمان والتشغيل

تطبق حدود صفحات الاستعلام وحقول API وأحجام الحدث، وفهارس المؤسسة/الوقت/الشدة/الحالة/الأصل، وحدود المعدل، وأحداث تدقيق مع طلب IP وUser-Agent/Request-ID دون تسجيل كلمات مرور أو مفاتيح. `/health` يفحص الخدمة السطحية، و`/ready` يتحقق من قاعدة البيانات وRedis والعامل على قدر ما يمكن رصده. اختار المستخدم خادماً خارجياً يملكه؛ لذا يبقى النشر على PostgreSQL/Redis/Celery ولا تنتقل بيانات الإنتاج إلى Manus WebDev.

## حدود التنفيذ الحالي

تحدد الشيفرة والاختبارات والـ migrations ما تحقق فعلاً؛ هذه الوثيقة تصميم وليست ادعاءً بأن كل بنود Part 2 أو النشر الإنتاجي أُنجزت. دعم SMTP/Slack/Teams ومزودي TI وتنفيذ إجراءات خارجية والتسجيل البريدي ونسخ الاحتياطي الفعلي تتطلب تكاملات وإعدادات مستقلة وموافقة عند الحاجة. لا يطلق أي فحص أو تكامل خارجي بلا إعداد صريح وتفويض.
